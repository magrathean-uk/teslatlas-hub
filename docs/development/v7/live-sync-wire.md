# Design: live-collected data on the signed sync wire

Status: G2-0 design, 2026-10-08, amended 2026-10-09 to match the hub-sync-v1@1.5.0 candidate. Not implemented. Revises the 2026-10-08 plan decision "the collector publishes physical changed-set packs" after reading the code; the plan row is updated to match this note. Anchors: `hub@6ac8ef0` (the Hub anchors added by the amendment read the same at `hub@b74a130`; `protocol/` anchors are this checkout) and the preserved App client (`A/`). The wire is `protocol/profiles/hub-sync-v1/1.5.0/` (status `candidate`, no Hub serves it); the `live_rules.*` keys named below are its machine-readable form, and where this note and the profile differ the profile wins.

## Problem

After a TeslaMate migration the App holds a PhysicalV3 checkpoint and follows physical heads. Physical heads are produced only by the importer from a sealed TeslaMate stage (`physical_publication.rs:139-300`); the live collector publishes lineage-2.1 deltas (`owner_supervision.rs:899-954`) which the App never requests (R05). Once Hub is the sole collector, live drives never reach the App through signed sync (PUB-05).

## Three walls in the current design

1. **Packs are bound to a head.** Every pack embeds `snapshot_id` and `head_sequence` (`sqlite_v2_2.rs:34-125`) and the App checks them (`hub_import_v22_stage.rs:2005-2008`), so a new head always means a full pack-set rewrite (about 126 packs for the household history).
2. **The wire is single-step.** The App requires `target.sequence == base + 1` (`hub_sync_v14.rs:166`), the Hub serves a stored transition only for `base + 1` (`hub_sync_v1.rs:838`), and only the transition whose target is the current head survives (the prior pending row is deleted, FK cascade on). An App two heads behind gets a full rebase (up to 1,771 chunks).
3. **No live-to-physical converter and no physical row store.** Live rows exist only as lineage-2.1 JSON (`materialised_*`); physical packs carry exact PostgreSQL shapes (`model.rs:949-1097`) with address and geofence id spaces that exist only inside the head packs; `charging_processes.position_id` is NOT NULL and live charges have no position id.

Consequence: "the collector publishes physical changed-set packs" as a per-commit operation is either O(history) per drive (rewrite the head) or needs a wire change. The plan's incremental-work target forbids the first.

## Decision

- **Target wire (hub-sync-v1 1.5.0, "live overlay"):** the import head stays as it is. Live changes become a second axis, `live_sequence`, served as the existing `teslatlas-physical-v3-delta-v1` changed-set format against the current head. The checkpoint carries `(receipt_id, manifest_sha256, head_sequence, live_sequence)`; `changes-since` returns the next live changed set when the head matches and `live_sequence` is behind, a `no_op` when current, `rebase_required` only when the base head is no longer the head to serve (a later import, or a fold, below). After a bootstrap or rebase the App fetches the live overlay immediately. Cost is O(affected rows) per publication; no pack rewrite.
- **One head behind is a full replacement.** A 1.5 client whose base is the immediate predecessor still gets a signed `rebase_required` with a complete replacement (up to 1,771 chunks), not the 1.4 stored N to N+1 changed set (`hub_sync_v1.rs:838`). That transition is safe only for a client at `live_sequence` 0, or if it were computed from the head at the client's live position; the profile offers it to neither (`checkpoint_resolution`, `live_rules.head_transition`).
- **Not chosen:** rebuilding a full head from the prior packs plus a live overlay on every drive close (no wire change, but O(history) per publication and 24 h retention of every superseded head: the pattern the plan forbids). Also not chosen: making JSON reads the live path for the App (two sources of truth in the offline cache, and the App's delta-apply code would go unused).
- **Interim:** lineage-2.1 publication stays until App v7 ships the 1.5.0 path; both publications run meanwhile. Lineage is retired afterwards (plan Decisions, Live sync wire).

## Shared core (Hub)

- (a) **Physical live-row store** `physical_v3_live_rows(vehicle_id, table_name, row_id, row_blob, digest, live_revision)` with an id seeding step for `addresses` and `geofences` taken from the head packs at head activation, and a second consumer cursor `physical_live_cursor(vehicle_id, published_revision, head_receipt_id)` over `sync_mutations`, because `claim_sync_mutations`/`published` is single-consumer and lineage still needs it.
- (b) **Converter** from `materialised_*` rows (cars, car_settings, drives, positions, charges, charge_samples, states, updates) to `Projection*V2_2` physical rows. Only closed drives and charges are converted (the same boundary as live commits: open-drive positions produce no mutation, `geofences_and_terrain.rs:391-416`), so every impacted root of a live changed set has `target_state` closed and a live changed set never needs to delete a root it published while open (`live_rules.live_roots_closed_only`; the profile's pack check refuses an open or absent root, `protocol/conformance/hub_sync_15.py:171-188`). A charge without a `position_id` gets the first position of its stationary span or a synthesised stationary position row. The synthesised row is an ordinary changed row: the 1.4 pack contract allows only the row roles `changed` and `context` (`protocol/profiles/hub-sync-v1/1.4.0/physical-delta-pack-v1.sql:245`), so nothing in the receipt marks it as synthesised.
- (c) **Trigger**: in `replay_export_outbox_blocking` (`owner_supervision.rs:810-861`) after the lineage publish, when the vehicle's physical state is `Public`, for mutations of drive close, charge close, state, update and car.
- (d) **Directed changed-set builder**: a constructor on `PhysicalDeltaComparison` that fills `row_versions` (side 1) and `edges` from the live store only, side 0 empty (live never deletes), then reuses `derive_changes`, `prepare_wire_scope`, `affected_months`, `DeltaOutput`, the receipt signer and `insert_physical_v3_delta_transition` with a new `live_sequence` column; `copy_target_context` reads roots from the head packs through `open_verified_physical_pack_2_2`. No scan of either head (removes the IMP-14 cost for live publication). The `target_raw_sha256` of a live changed set is not computed from the live store: it is the head's own all-history commitment, the sealed stage digest the importer passed when it published the head (`physical_publication.rs:251-258`), identical in every live step of the head (`live_rules.target_raw_sha256`). The Hub therefore keeps that commitment with the head for as long as the head is served; the step itself is bound by the signed `(receipt_id, manifest_sha256, from_live_sequence, to_live_sequence)`.
- (e) **Journal** `physical_v3_live_journal(vehicle_id, live_sequence, from_revision, to_revision, receipt_json, pack digests, published_at_ms)`. It is not pruned by a watermark over paired devices or by a retention window alone: a new, reinstalled or rebased device and a 1.4 upgrade start at `live_sequence` 0 and need step 1, which no paired device's acknowledgement protects. The Hub keeps every live changed set of the current head from `live_sequence` 1, or folds the live rows into a new head before pruning (`live_rules.live_journal_retention`); a fold is a head rotation the journal alone can trigger. Packs are served through the existing pack handler with the vehicle-scope check.
- (f) **Head ledger**: for every head ever published for a vehicle, for the vehicle's life, its identity (`manifest_id`, `receipt_id`, `manifest_sha256`, `sequence`, source binding), the live position the Hub holds for it and the highest `live_sequence` it ever signed for it (the high-water mark) (`live_rules.head_identity_members`, `head_live_members`). Without it an App on a head whose packs expired after 24 h, or offline beyond retention, would get an error instead of `rebase_required`. The cost is one row per head per vehicle.
- (g) **Base resolution**, first match wins (`live_rules.base_resolution`), in this order: (1) an identity the ledger does not record, or records differently (for example the digest of the 1.4 manifest of the same head): unsigned `422 unknown_base_receipt`; (2) a base that is not the head to serve: signed `409 rebase_required` with a replacement that already exists; (3) a rotation pending for the head to serve: a transient failure the profile does not define; (4) `base_live_sequence` above the head's high-water mark: the `422`; (5) above the head's position and not above the mark: a transient failure, and the Hub starts a rotation; (6) equal: the signed live `no_op`; (7) behind: the next live changed set. The Hub never builds a replacement inside a request (a fold is O(history) and the client chooses `base_live_sequence`): it starts the rotation outside the request and pauses live service for the head meanwhile (`live_rotation_inside_request`). Anything that can lower a position (a backup restore, a lost journal tail) rotates the head before live service resumes; a restore also rolls the ledger back, so an App on a head the restored ledger no longer records gets the `422` and bootstraps.
- (h) **One changed set per step**: a `(receipt_id, manifest_sha256, live_sequence)` is signed for at most one changed set and a replay returns identical content (`live_step_content_is_unique`). A live publication that cannot fit the 1.4 admission limits or closure in one step is split into consecutive live steps, each closed over its own roots (`live_over_limit`).

## Protocol change (hub-sync-v1 1.5.0)

- Request adds `base_live_sequence`; receipt adds `live_sequence`, `from_live_sequence`, `to_live_sequence`; manifest adds a signed `live_sequence` that is 0 for the life of the head. It is not the head's current overlay position: a moving signed member would change the head's `manifest_sha256`, which the Hub derives by re-signing the manifest (`manifest_signing.rs:66-93`), and the head identity would move with every live step. The current position is learned through `changes-since` (`live_rules.manifest_live_sequence`). A 1.5 manifest therefore differs from the 1.4 manifest of the same head by that member, and the 1.4 digest is never a 1.5 base. `accepted_changed_set_formats` unchanged. Discovery capability token `sync.live`, advertised only when the Hub serves the overlay and the discovery profile it names defines the token: `hub-http-v1@1.2.0` and `1.1.0` do not, so a Hub serving 1.5 under them does not advertise it until a later `hub-http-v1` minor adds it (`capability`).
- Rules: a live changed set is valid only for the exact head `(receipt_id, manifest_sha256)`; `to_live_sequence == from + 1`; a later import rotates the head, resets `live_sequence` to 0 and folds the live rows into the new stage (below), so a client whose base is not the head to serve gets a signed `rebase_required` with a complete replacement and a retry from `base_live_sequence` 0, whatever its live position and even one head behind. The reasons are `head_changed` (a later import), `live_retention` (a fold pruned the journal of the requested head) and `live_ahead` (the head was rotated away after a regression); they are diagnostic and the App takes the same action for each. None is an error, including for a head whose packs expired.

## Importer interaction (the hard part)

- A later migrate captures a pure TeslaMate stage. Rotating it would leave every live-only row out of the new head. Rule: the importer unions the live-row store into the sealed stage before publication (one pass, keyed by `(table, id)`), under the publication gate, and fences the live cursor at capture time so rows published after the fence are re-published against the new head.
- Id collisions: live ids are seeded from the import state (`projection.rs:811-890`); if TeslaMate kept writing after handover, its new ids can collide with live ids. Handover (G2-4) requires TeslaMate stopped before the final snapshot; the union step rejects a collision with a differing digest and blocks the rotation with an actionable report rather than merging.
- A drive captured both live and by TeslaMate is a duplicate; the union keeps the TeslaMate row (supplied values win) and the live row is simply absent from head N+1. No transition tombstones a live row. The 1.4 transition from head N to N+1 is computed from head N's packs, that is at `live_sequence` 0, because a 1.4 client never holds live rows; it carries every folded live row of N+1 as a changed row (`live_rules.head_transition`: base `head_packs_at_live_sequence_0`, `tombstones_live_rows` false). A 1.5 client above `live_sequence` 0 never receives that transition: it takes the complete replacement of N+1.

## App v7 (the App writer)

- Checkpoint stores `live_sequence` beside the `hub_sync_22_*` metadata; requests carry it; the `target == base + 1` rule becomes "same head, advancing live sequence"; `stage_and_verify_delta`, `project_and_apply_delta` and `invalidate_physical_delta_maps(affected_months)` are reused unchanged.
- Apply: a live changed set applies only when the stored `(receipt_id, manifest_sha256, live_sequence)` equals the receipt's base and `from_live_sequence`, and then activates `(receipt_id, manifest_sha256, to_live_sequence)` atomically. A live receipt's target is the head the App already holds, so the 1.4 clause that replay of an already activated target is idempotent does not apply: replay identity includes the live position, and a receipt is a replay only when the stored `live_sequence` already equals `to_live_sequence` (`live_rules.live_apply`). The App rejects `to != from + 1`, a receipt for another head, and a second, different receipt for one step.
- Errors: on `422 unknown_base_receipt` the App drops its checkpoint, bootstraps under the 1.5 selector and then requests with `base_live_sequence` 0; it never retries the same request. On a transient failure it keeps the checkpoint and retries the same request later. After a bootstrap or a rebase it requests the overlay at once from 0.
- Upgrade from 1.4: the App fetches the 1.5 manifest of the head the Hub serves, and adopts it at `live_sequence` 0 when `vehicle_id`, `manifest_id`, `receipt_id`, `sequence` and schema match its 1.4 checkpoint (and the chunk list, when it holds the 1.4 manifest rather than a changed set's target). It keeps its materialised state, stores the 1.5 manifest digest, and keeps the 1.4 digest beside it until the head changes. If the Hub later stops serving 1.5, an App at `live_sequence` 0 resumes 1.4 from the kept checkpoint; an App above 0 holds rows no 1.4 head contains and does a full 1.4 bootstrap (`checkpoint_upgrade`).

## Risks and tests

- Gate hold: live publication must never take the long rotation path; it runs under the existing flock gate but is bounded by the changed set size (minutes become milliseconds). One exception: a single root whose closure alone cannot fit the 1.4 limits folds into a new head and answers `head_changed` (practically unreachable). Any other oversized publication is split into consecutive live steps, each closed over its own roots, never a rotation (`live_over_limit`, `live_fold_only_for`).
- Three sequence axes (physical head, lineage, mutation revision) plus `live_sequence`: a mapping table and an idempotent crash replay (60 s claim lease) are required; a test interrupts publication after the journal insert and before the pack commit and expects one logical result.
- Open drives: the converter publishes only closed roots; a test ends a drive after a restart and expects exactly one transition.
- Fidelity: a live row may differ from the TeslaMate row of the same drive at the next import; the union step's digest rule above decides, and the test imports a snapshot containing a drive already live-published.
- Retention: `sync_mutations` is never pruned today. The live journal is not pruned by a watermark: the Hub keeps every live step of the current head from `live_sequence` 1 or folds first (Shared core (e)). An App on a superseded head, offline beyond retention, or on a head whose packs expired gets `rebase_required`, not an error, because the head ledger keeps every head's identity for the life of the vehicle (Shared core (f)). A test starts a client at `live_sequence` 0 after a long run of steps and expects step 1; a test restores a backup and expects the head to rotate before live service resumes, a client of a head newer than the restored ledger to get the `422` and recover by a bootstrap, and no `200` from a head with a pending rotation.
- Position and replay: a test names a position above the high-water mark and expects the `422` with no rotation; one names a position above the head's position and not above the mark and expects a transient failure, a rotation outside the request, and then a `409` `live_ahead` for the rotated head. A test asks for one step twice and expects identical content.
- Open, not decided here: how a device that starts at `live_sequence` 0 catches up, and what the journal costs. With periodic folds, every fold forces every 1.5 client, fully current ones included, into a full replacement of up to 1,771 chunks, the cost the Problem section and watermark pruning were meant to avoid. Without folds the profile serves one step per response and the manifest stays at 0, so a new device, a reinstall, a rebased client or a 1.4 upgrade replays every live step of the head since it was published, one signed `changes-since` request and one pack fetch per step, and the journal grows without bound once TeslaMate is stopped at handover (no import rotates the head again; every drive close, charge close, state, update and car mutation publishes a step, Shared core (c)). The options are periodic folds, a bounded multi-step catch-up response, and a bootstrap that carries the live rows (which would give the manifest's `live_sequence` member a meaning; dropping the member so 1.4 and 1.5 manifests of a head are byte-identical would close that option). It is decided in the batch that implements live publication in the Hub, and the candidate profile may change before a Hub serves it.
- Acceptance (plan journey 7): a drive collected after handover appears in the App through `changes-since` without a bootstrap, with the affected month's prepared map invalidated and regenerated.
